# ADR 0003：每个客户端一个有界队列 + 独立写线程

- 状态：已接受
- 日期：2026-11-14
- 关联：[API.md](../API.md)「并发与丢帧」、[AGENTS.md](../../AGENTS.md) §1

## 背景

旧实现把「采集/编码」和「发给客户端」放在同一根线程上，且直接同步写 socket：

- 视频：`handle()` 里 `while (deadline) { out.write(jpg); out.flush(); }`
- 音频：`AudioStream` 泵线程里 `synchronized (clients) { for (Socket s : clients) { o.write(...); o.flush(); } }`

Java 的 `Socket` **没有写超时**（`setSoTimeout` 只管读），所以对端不读数据时
`write()` 会永久阻塞。后果：

| 场景 | 旧行为 |
|---|---|
| 一个视频客户端卡住（暂停的标签页 / 拔网线的笔记本 / 半死 TCP） | 该连接线程永久卡在 `write`，30 分钟 deadline 永远等不到 |
| 一个音频客户端卡住 | 持锁写 → 音频泵和其他所有客户端一起锁死 |
| 一个 `/ts`（H.264 实验通道）客户端卡住 | 同上，持锁写，编码与推流一起停 |
| 多人同时看 | 每连接一个线程、无上限 → 线程与内存可被耗尽 |

本机对照实测（`verify/OldStyleTest.java`，localhost 真 socket，一个客户端从不读数据）：
**300 帧任务在 3 秒内只投递了 1 帧，生产者仍阻塞在 write 上。**

## 决策

新增 `src/com/droidlogic/app/ClientChannel.java`：**每客户端一个有界队列 + 独立写线程**。

1. 生产者只调 `offer(byte[])`：入队 + 超限丢最旧，全程 O(1)、永不阻塞、不抛异常；
2. 真正的 `write()` 在各自的 `send-*` 线程里，慢端只慢自己；
3. 队列上限：视频 `/raw` `/stream` 3 帧 / 512 KB，音频 `/pcm` 32 块 / 64 KB，
   `/ts` 32 块 / 512 KB（帧数或字节先到先算）；
4. 视频客户端总数上限 `MAX_VIDEO_CLIENTS = 8`，超限直接回文本 `too many viewers` 并断开；
5. `close()` 关闭 socket，把阻塞中的 `write` 踢出来；写线程连续 `STALL_MS`(30s)
   没有一次成功写入，就在下一次 `offer()` 时判定僵死并关闭；
6. 断开探测放在处理线程（`waitForPeerClose`）：流式端点客户端不发数据，
   `read()` 只会等到 EOF，所以能**立刻**发现断开，不依赖"下一次写失败"。

## 被否决的方案

| 方案 | 为什么不行 |
|---|---|
| 给 socket 加写超时 | Java 没有这个 API，`setSoTimeout` 只作用于 `read` |
| 调大 socket 发送缓冲区 | 只是把"多快卡住"往后推，卡住后行为不变 |
| 阻塞时直接丢帧（不加队列） | 编码线程仍会被 `write` 拖住，只是少写几帧 |
| 每个客户端独立编码 | CPU 翻倍；实测编码不是瓶颈，共享一路编码才是对的 |
| 支持多路音频客户端 | 属行为变更（现文档声明 `aclients` 上限 1），本次不动，另行确认 |

## 后果

**正面**
- 慢客户端不再影响采集、编码和其他观看端（本机实测：快端 300/300 帧全收）；
- 积压有硬上限，内存可预测（8 端 × 512 KB = 4 MB 上限，96 MB 堆下安全）；
- 客户端断开能被立刻回收，不再依赖"下一次写"；
- 客户端数有上限，线程不会被耗光。

**负面**
- 每个客户端多一根线程 + 最多 3 帧的内存；
- 队列满时**会丢帧**（丢最旧的），这是有意的取舍：直播场景下延迟比完整更重要；
- 音频每块多一次 `Arrays.copyOf`（约 2 KB / 块，94 块/秒 ≈ 190 KB/s），可忽略但确实存在。

## 验证

| 项 | 结果 |
|---|---|
| 已编译 | ✅ `bash tools/build.sh` → `build/classes.dex`（40168 → 45572 字节） |
| 已自测（本机） | ✅ `verify/SlowClientTest.java` 5 项全 PASS，连跑 3 次稳定 |
| 对照（旧实现） | ✅ `verify/OldStyleTest.java` 3 秒只投递 1 帧即卡死 |
| 已真机验证 | ❌ **未做**。需要在电视上跑起来，用两个浏览器（一个正常、一个暂停）确认 |

自测实测值：生产者单次 `offer()` 最大 0.07–0.21 ms、平均 0.009–0.015 ms；
慢端积压峰值恰好等于上限 3 帧，累计丢弃 295/300 帧；快端收到 19660800 字节（100%）。
