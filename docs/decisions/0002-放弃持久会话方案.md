# ADR 0002：放弃 ScreenManager 持久会话方案

- 状态：已拒绝（做过验证，结论是不可行）
- 日期：2026-11-06

## 背景

厂商接口 `startScreenCapBuffer` 每采一帧都要完整走一遍
`init → start → readBuffer → stop → reset → uninit`，光"等源端出帧"就固定 30–33 ms，
这是帧率上不去（约 18 fps 上限）的根本原因。

`libscreencontrolservice.so` 里导出了 `android::ScreenManager`，看起来可以：
`init()` 一次 → `start()` 一次 → 循环 `readBuffer()`，绕开逐帧重启。

如果成立，帧率理论上能到 30 fps 以上。

## 做了什么

1. 用 `llvm-objdump --triple=thumbv7-linux-androideabi` 反汇编，还原了：
   - `init(w, h, fps, datatype, &clientId, sp<IGraphicBufferProducer>)`
   - `start(clientId)` / `stop(clientId)` / `readBuffer(clientId, sp<IMemory>, &timestamp)`
2. 确认 `ScreenManager` 跑在**调用方进程**里（日志以我们自己的 pid 打印），
   所以可以直接 `new` 一个出来。
3. 解决了 `sp<IMemory>` 的 ABI 问题：`IMemoryHeap` 是虚继承，`sp` 里必须是
   "调整过的子对象指针"。反汇编 `IMemory::pointer()` 得到算法：

   ```
   heap  = getMemory(&offset)     // 虚函数
   adj   = heap + vtable[-12]     // 虚基类偏移
   return adj->getBase() + offset
   ```

   然后伪造 `IMemory`（64 项 vtable 指向同一 stub，返回真实 `MemoryHeapBase`）。
4. `init rc=0`、`start rc=0`，screen source 成功启动。

## 结果

**`readBuffer` 一律返回 1（无帧），耗时 0.0 ms。**

反汇编早退分支确认：

```asm
7786: beq 0x781c       ; if ([this+0x28] == 0)
7834: movs r5, #1      ; return 1，不打日志
```

标志位要靠**采集线程**置位，而采集线程的代码不在 `libscreencontrolservice.so` 里：

```
/system/bin/screencontrol 引用：
  android::ScreenCatch::setVideoCrop(int,int,int,int)
  libstagefright_screencatch.so     ← 帧泵在这里（28 KB）
```

`libscreencontrolservice.so` 里**没有** `threadFuncForScreenManager` / `ScreenCatch`。

## 决策

**放弃。** 要打通就得把守护进程的采集管线整个复刻
（加载 `libstagefright_screencatch.so`、构造 `ScreenCatch`、接线程与 HIDL 客户端），
那已经等于重写厂商守护进程，工作量以天计，失败时还可能把电视屏幕通路搞坏。

## 后果

- 帧率锁死在约 18 fps，只能靠降分辨率换取流畅度。
- 已实测确认这不是客户端问题：native 客户端（绕开 Java 拷贝）与 Java 版耗时一致
  （640×360：69.6–74.9 ms vs 71.7 ms）。
