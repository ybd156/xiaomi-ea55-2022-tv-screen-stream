# 实测数据

> 全部在目标电视（[DEVICE.md](DEVICE.md)）上测得，2026-11-06。
> 单次粗测，未做多次取平均，**不代表长期稳定表现**。

## 1. 裸采集帧率（只 grab，不编码）

方法：`bench` 模式，每档连测 5–6 帧取平均。

| 输出尺寸 | 单帧耗时 | 帧率 |
|---|---|---|
| 1920×1080 | 306 ms | 3.3 fps |
| 1280×720 | 166 ms | 6.0 fps |
| 960×540 | 104 ms | 9.6 fps |
| 640×360 | 72 ms | 14.0 fps |
| 480×270 | 60 ms | 16.6 fps |
| 320×180 | 40 ms | 25.1 fps |

### 耗时构成（960×540，从 logcat 时间戳拆解）

| 阶段 | 耗时 |
|---|---|
| 请求 → `start AML_SCREEN_SOURCE` | ~1 ms |
| 等源端出第一个非空帧 | ~30–33 ms（固定） |
| 读回 + stop/reset/uninit | ~70 ms（随像素量线性） |

扣掉固定等待后，**拷贝带宽约 30 MB/s**。

## 2. MJPEG 端到端（采集 + 编码 + HTTP 推送）

`serve` 模式，采集与编码分两条线程，JPEG q70。

| 输出尺寸 | 帧率 | 每帧 | 码率 |
|---|---|---|---|
| 960×540 | 8.7 fps | ~65 KB | 5.0 Mbps |
| 640×360 | 14.9 fps | ~40 KB | 4.8 Mbps |
| 480×270 | 17.2 fps | ~27 KB | 3.8 Mbps |
| 320×180 | 18.3 fps | ~14 KB | 2.1 Mbps |

### 单线程 vs 双线程

| 尺寸 | 单线程（抓→编串行） | 双线程（流水线） | 提升 |
|---|---|---|---|
| 960×540 | 6.8 fps | 9.4 fps | +38% |
| 640×360 | 11.9 fps | 14.8 fps | +24% |

## 3. H.264 推流

`OMX.google.h264.encoder`（**软件编码**，这台机器没有硬件编码器）。

| 输出尺寸 | 帧率 | 码率 |
|---|---|---|
| 640×360 | 12.9 fps | ~650 kbps |
| 480×270 | 14.7 fps | ~325 kbps |
| 320×180 | 17.4 fps | ~360 kbps |

**结论**：
- 带宽比 MJPEG 省 7–15 倍
- 但帧率**更低**（多了 RGBA→NV12 转换），延迟也更高（+0.5~1 s）
- 局域网内没优势，只在走 VPN / 公网时有价值

## 8. 空闲停采（2026-11-20，真机实测）

旧实现只要进程活着就按接口能吃下的速度跑满采集与编码，与「有没有人在看」无关。
2026-11-20 加了空闲判定：`clients==0` 持续超过 `idleMs`（默认 30 s）就停止抓帧。

### CPU 对比（480×270，单位：占单核百分比，4 核机器）

| 状态 | `app_process` | `screencontrol` | 合计 |
|---|---|---|---|
| 有人观看（18 fps） | 47% | 44% | 0.91 核 |
| 无人观看（idle） | 8% | 4% | 0.12 核 |

降幅约 87%。测法：读 `/proc/<pid>/stat` 的 utime+stime 差值，采样窗口 4 秒。
空闲态残留的 8% 主要来自仍在小跑的音频泵（读取并下混 8ch PCM）。

### 行为验证

| 用例 | 结果 |
|---|---|
| `-Dtvss.idleMs=1500` 启动后 2 s | 日志出现 `idle: 无人观看超过 1 秒，暂停采集（gen=1）`；`/stats` 为 `fps=0, idle=true`，`frames` 冻结 |
| 接入一路 `/raw` | 2 s 内 `/stats` 变 `idle=false, clients=1`；8.1 s 收到 2.2 MB（≈2.2 Mbps），确认恢复出流 |
| 断开 4 s | 重新 `idle=true` |
| 空闲态 `GET /snap` | `frames` 503 → 504，返回 480×270 / 24.5 KB 新帧；之后仍 `idle=true` |
| 默认 30000 ms 阈值 | 恢复路径同样出流（接 `/raw` 即恢复） |

### 两条不做的取舍

- **音频不停**：`tinycap` 反复开关会让 loopback 退化到「能打开但不产数据」，只能重启电视恢复（见 [PITFALLS](PITFALLS.md)），风险远大于它约 0.8% 的 CPU。
- **采集线程不销毁**：空闲态在同一个线程里睡，避免「起新管线时旧线程卡在 `native_ScreenCapBuffer` 里」导致厂商会话泄漏（同见 [PITFALLS](PITFALLS.md)）。

### 副作用

- 看门狗必须识别 `idle`（否则「30 秒没新帧」会误判卡死并反复重启管线，10 分钟内 3 次还会误杀进程），已在 `startWatchdog` 里跳过。
- `/stats` 的 `kbps` 是「最后一帧大小 × 平均帧率」，空闲归零、静止画面虚低，**不能当带宽用**。

## 11. VDIN 直采模式（`serve-vdin`，2026-11-21）

> 状态：**已真机验证**（采集+编码+HTTP 全链路），但**不是默认模式**，需要 screencontrol 不占用 `/dev/video12`。

绕过厂商的每帧 `start→等首帧→读回→stop`，直接对 `/dev/video12` 开常开 V4L2 流，格式 NV21，
再用 `YuvImage` 直接压 JPEG（**不做 RGBA 转换**）。

### 11.1 帧率对比（10 秒窗口）

| 分辨率 | 厂商路径 | `serve-vdin` | 倍数 |
|---|---|---|---|
| 480×270 | 16.6 fps | **30.1 fps** | 1.8× |
| 960×540 | 8.3 fps | **30.4 fps** | 3.7× |
| 1280×720 | 5.5 fps | **30.2 fps**（裸采集） | 5.5× |
| 1920×1080 | 3.0 fps | **30.3 fps**（裸采集） | 10× |

**关键性质：帧率与分辨率解耦**，恒定 30 fps（显示管线 60 Hz，隔帧取）。

### 11.2 新的瓶颈：码率

960×540 / q70 / 30 fps 时 `/raw` 实测 **13 Mbps**（厂商路径同分辨率只有 ~3 Mbps，因为只有 8.3 fps）。
也就是说采集快了之后，**MJPEG 的帧内编码成了新瓶颈**：
- 480×270：5.6 Mbps（可接受）
- 960×540：13 Mbps（ZT 链路上会排队）
- 想上高分辨率必须换 H.264（预计 ~1 Mbps 量级，未实施）

### 11.3 使用前提与限制

- `/dev/video12` 是独占设备，**必须先停 screencontrol**（`stop screencontrol` + `killall`）。
  停掉后 MiTV 自身的截图/录屏能力会失效。
- 启动参数：`serve-vdin 1 <w> <h> <port> <outW> <outH> <q>`，其余端点行为不变。
- `/set` 已适配：会重开设备换尺寸，不会掉回厂商管线（早期版本会因此崩进程）。
- 看门狗在 VDIN 模式下不做「帧数不涨」判定（重启会走厂商接口，必然失败）。
- **开机自启仍是厂商模式**（`tv-screen-stream.sh` 起的是 `serve`），VDIN 需要手动切换。

### 11.4 JPEG 质量档位（实测 `/raw`，10 秒窗口）

帧率与质量无关（都 ~30 fps），只有码率变：

| 配置 | 实测帧率 | 实测码率 | 平均每帧 |
|---|---|---|---|
| 960×540 q70 | 30.3 fps | 13.0 Mbps | ~54 KB |
| 960×540 q45 | 30.3 fps | **10.6 Mbps** | 41.5 KB |
| 480×270 q70 | 30.1 fps | ~5.6 Mbps | ~23 KB |
| **480×270 q45（推荐）** | **30.5 fps** | **4.4 Mbps** | 18.4 KB |

> 注意：`VDINSTAT` 日志里的 `jpeg=KKB` 只是**单帧采样**，碰巧取到静态画面时会明显偏小
> （实测日志说 21–25 KB，真实平均 41.5 KB）。判断码率一律用 `/raw` 累计字节。

**推荐：480×270 / q45 / 30 fps ≈ 4.4 Mbps** —— 相比原厂商路径（480p / 16.6 fps / ~5 Mbps），
帧率 1.8×，码率略低。960×540 要 10.6 Mbps，ZT 链路上会排队，除非走局域网。

### 11.5 开机默认 + 音频验证（2026-11-21 04:20）

`deploy/tv-screen-stream.sh` 已改为 **VDIN 优先**（安装到 `/data/adb/service.d/`）：

- 默认 `TVSS_MODE=serve-vdin`、`480x270`、`q45`（可用环境变量覆盖）
- 起服务前先 `stop screencontrol` 并轮询确认它真的退出（它握着 `/dev/video12`）
- **VDIN 起不来自动回退 `serve`**（并 `start screencontrol`），不会让电视没画面
- 看护循环每 20 秒：进程挂了就拉起；**若 `screencontrol` 又出现（MiTV 会自己拉），重新停掉**
- 缺 `libvdin.so` 时自动降级为 `serve`

**踩坑（重要）**：脚本里的 `DEX=/data/local/tmp/sc.dex`。本轮把新 dex 推到了 `sc-vdin.dex`，
导致脚本跑到的是旧 dex —— 旧 dex 不认识 `serve-vdin`，落进 `single()` 分支采一帧就退出，
日志表现为「VDIN 起不来，回退厂商模式」。**换 dex 必须覆盖 `sc.dex` 本身。**

端到端实测（改完后）：

| 项 | 结果 |
|---|---|
| 视频 | 480×270 / **30.3 fps** / **3.8 Mbps** |
| 音频 | `apeak=87`、`abytes` 持续增长、`/pcm` 实测 191,488 B/s（实时 192,000，99.7%） |
| `/snap` | 480×270 / 14.4 KB 正常 |
| 进程 | `serve-vdin 1 480 270 8899 480 270 45`，`screencontrol` 为空 |
| 看护实战 | 日志出现 `screencontrol 又出现了，重新停掉`，之后稳定 30 fps |

> 音频不经过 VDIN，走原 `tinycap` 8 声道下混路径，VDIN 模式下未受影响。

## 9. 遥控注入延时（2026-11-21，真机实测）

**根因**：旧实现每次 `Runtime.exec("input keyevent N")`。`/system/bin/input` 是 shell 脚本，
每次都要新起一个 ART 虚拟机。

| 操作 | 实测（10 次平均） |
|---|---|
| `input keyevent 0`（KEYCODE_UNKNOWN，无副作用） | **846 ms** |
| `input --help`（只启动，不做任何注入） | 838 ms |
| `sendevent`（单条 evdev 事件） | 55 ms |
| `/system/bin/true`（纯 fork+exec 基线） | 27 ms |
| 5 次并发 `input keyevent` | 1.43 s（各自起 JVM，互相争核） |

→ 846 ms 里 820 ms 是 JVM 冷启动，按键事件本身接近 0。代码注释里写的「约 30–80 ms」与实测差一个数量级。

**改法**：`InputManager.injectInputEvent`（反射），一次 binder 调用；失败退回 `input` 且不再 `waitFor`。

| 指标 | 改前 | 改后 |
|---|---|---|
| `/key` 往返（PC → 电视 → 回包） | ≈ 880 ms | **50–60 ms** |
| 其中网络 | — | 32 ms（`Connection: close` 每请求两次往返） |
| 其中注入 | 846 ms | **1–3 ms** |
| `injectFallback` | — | 0（8/8 走快速通道） |

**端到端感知**（按下去到电视画面变化）：请求 32 + 注入 3 + 电视 UI 响应 ~50–100 + 等下一帧 ≤57 + 回传 16
≈ **100–200 ms**，改前约 0.95–1.0 s。

**顺带修复**：入站 socket 关掉 Nagle（`setTcpNoDelay(true)`）。实测服务端处理本身已接近 0 ms
（裸 socket：connect 16 ms，发出请求后 17 ms 收到首字节），所以 Nagle 不是主因，属防御性加固。

**验证注意**：令牌默认每次启动随机生成，用旧令牌测 `/key` 会拿到 403（往返仅 34 ms，看起来"很快"但**根本没注入**）。
判据要看 `/stats` 的 `injectOk` 是否增长。
