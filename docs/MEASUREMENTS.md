# 实测数据

> 全部在目标电视（[DEVICE.md](DEVICE.md)）上测得，2026-11-06。
> 单次粗测，未做多次取平均，**不代表长期稳定表现**。

## 1. 裸采集帧率（只 grab，不编码）

方法：`bench` 模式，每档连测 5–6 帧取平均。

| 输出尺寸 | 单帧耗时 | 帧率 |
|---|---|---|
| 1920×1080 | 306 ms | 3.3 fps |
| 1280×720 | 166 ms | 6.0 fps |
| 960×540 | 104 ms | 9.6 fps |
| 640×360 | 72 ms | 14.0 fps |
| 480×270 | 60 ms | 16.6 fps |
| 320×180 | 40 ms | 25.1 fps |

### 耗时构成（960×540，从 logcat 时间戳拆解）

| 阶段 | 耗时 |
|---|---|
| 请求 → `start AML_SCREEN_SOURCE` | ~1 ms |
| 等源端出第一个非空帧 | ~30–33 ms（固定） |
| 读回 + stop/reset/uninit | ~70 ms（随像素量线性） |

扣掉固定等待后，**拷贝带宽约 30 MB/s**。

## 2. MJPEG 端到端（采集 + 编码 + HTTP 推送）

`serve` 模式，采集与编码分两条线程，JPEG q70。

| 输出尺寸 | 帧率 | 每帧 | 码率 |
|---|---|---|---|
| 960×540 | 8.7 fps | ~65 KB | 5.0 Mbps |
| 640×360 | 14.9 fps | ~40 KB | 4.8 Mbps |
| 480×270 | 17.2 fps | ~27 KB | 3.8 Mbps |
| 320×180 | 18.3 fps | ~14 KB | 2.1 Mbps |

### 单线程 vs 双线程

| 尺寸 | 单线程（抓→编串行） | 双线程（流水线） | 提升 |
|---|---|---|---|
| 960×540 | 6.8 fps | 9.4 fps | +38% |
| 640×360 | 11.9 fps | 14.8 fps | +24% |

## 3. H.264 推流

`OMX.google.h264.encoder`（**软件编码**，这台机器没有硬件编码器）。

| 输出尺寸 | 帧率 | 码率 |
|---|---|---|
| 640×360 | 12.9 fps | ~650 kbps |
| 480×270 | 14.7 fps | ~325 kbps |
| 320×180 | 17.4 fps | ~360 kbps |

**结论**：
- 带宽比 MJPEG 省 7–15 倍
- 但帧率**更低**（多了 RGBA→NV12 转换），延迟也更高（+0.5~1 s）
- 局域网内没优势，只在走 VPN / 公网时有价值

## 4. 音频

| 项 | 值 |
|---|---|
| 采样率 | 48000 Hz |
| 采集声道 | **8**（必须，2 声道会失败） |
| 下发声道 | 2（下混 ch0/ch1） |
| 位深 | S16LE |
| 码率 | ~1.5 Mbps |

### 音量与采集幅度的关系

| 电视音量 | 采集峰值 | RMS |
|---|---|---|
| 音量 3 / 100 | 2632 | 376 |
| **音量 0（静音）** | **63** | — |

→ 这是「音量之后」的抽头，**电视静音时采不到声音**。

## 5. 硬件解码能力

| 源 | 输入 fps | 输出 fps | 丢帧 |
|---|---|---|---|
| 1280×720 H.264 | 25 | 25 | 0 |
| 1920×1080 H.264 | 60 | 60 | 0–1 |
| **3840×2160 H.264** | **60** | **32** | **27** |

4K60 H.264 超过 SoC 能力，会丢一半帧。1080p 及以下满帧。

## 6. 资源占用

| 项 | 值 |
|---|---|
| `app_process` RSS | 74–76 MB（`-Xmx96m`） |
| 整机 CPU 增量 | 约 +1.3 ~ +1.8 核（4 核机器） |
| 整机内存 | 1.5 GB，采集时剩余 130–230 MB |
| 电视本机播放影响 | **无**（`frame count` 仍 25 fps、`drop count` 0） |

## 7. 已证伪的优化方向

| 方向 | 结论 | 证据 |
|---|---|---|
| 用 native 客户端绕开 Java 拷贝 | ❌ 无用 | 640×360：原生 69.6–74.9 ms vs Java 71.7 ms |
| 多线程并发采集 | ❌ 收益 12% 但 CPU 翻倍 | 960×540：1 线程 9.9 fps → 2 线程 11.1 fps |
| 降 JPEG 质量 | ❌ 不影响帧率 | q70 11.6 fps vs q55 11.5 fps |
| GE2D 硬件加速 | ❌ 帮不上帧率 | 瓶颈在采集侧，不在编码 |
| `ScreenManager` 持久会话 | ❌ 帧泵不在可及库内 | 见 [ADR 0002](decisions/0002-放弃持久会话方案.md) |
| 换硬件编码器 | ❌ 这台机器没有 | 见 [DEVICE.md](DEVICE.md) 4.2 |
